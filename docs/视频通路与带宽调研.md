# 540P→1080P FPGA 视频通路与带宽调研

> 适用项目：ACX750-200T 上的 FSRCNN 风格 `2×` 视频超分辨率系统
> 冻结目标：`960×540 Y8 → 1920×1080 Y8，30 FPS`
> 调研日期：2026-09-24

## 1. 先说结论

1. **当前算法的有效视频数据带宽并不高。**Y8 模型输入与输出相加为 `77.76 MB/s`；即使外围采用 RGB888，输入与输出有效载荷相加也只有 `233.28 MB/s`。
2. **不能把中间特征图反复写入 DDR。**本模型五级中间特征每帧约 `51.84 MB`；若每级均写入后再读回，30 FPS 仅中间特征就需要约 `3.1104 GB/s`，还未计视频帧、刷新、突发间隙和控制器损耗。正确方案是用 BRAM 行缓存组成逐层流水线。
3. **算法算力比视频 I/O 更紧。**模型需要 `1.4681088 GMAC/帧`，30 FPS 为 `44.043264 GMAC/s`。按 180 MHz 理想估算，至少要持续完成约 `244.7 MAC/周期`；实际并行度还要为流水空泡、边界和布局布线留余量。
4. **ACX750-200T 没有 ARM/PS，也没有公开资料所列的板载 HDMI 输入。**它是 `XC7A200T` Artix-7 纯 FPGA 板；底板资料明确列出 `HDMI TX`，未列 `HDMI RX`。因此先前 PYNQ-Z2 的“PS 控制、HDMI 输入”结构不能直接复用。
5. **建议分两阶段实现。**近期先做“DDR/ROM 测试视频 → 超分核 → 帧缓存 → HDMI TX”；获得稳定结果后，再增加外接 HDMI RX、PCIe 或千兆以太网输入。不要让输入接口阻塞算法 IP 验证。

## 2. 板卡事实与边界

### 2.1 已确认硬件

| 项目 | 已确认信息 | 对本项目的含义 |
|---|---|---|
| FPGA | XC7A200TFBG484-2 | 纯 Artix-7，没有 Zynq 的 ARM/PS |
| 逻辑资源 | 134,600 LUT、269,200 FF | 控制、窗口、加法树资源较充足 |
| DSP | 740 个 DSP Slice | 180 MHz 时理论峰值按 1 MAC/DSP/周期为 133.2 GMAC/s |
| 片上存储 | 13,140 Kb BRAM，约 1.64 MB | 可放行缓存和全部模型参数，放不下一整帧 RGB 1080P |
| 外部存储 | 两颗 16-bit DDR3 组成 32-bit 总线；单颗 512 MB | 容量足够做多帧缓存；实际频率和效率须看 MIG 配置与实测 |
| 视频接口 | 板载 HDMI TX | 可以输出显示；没有证据表明底板自带 HDMI RX |
| 其他入口 | PCIe、千兆以太网、GPIO/板间连接器 | 可作为后续实时输入候选 |

### 2.2 必须向老师或硬件成员确认的四件事

- 比赛实际提供的是不是完整 ACX750 底板，而非只有核心板。
- 是否另配 HDMI RX、摄像头或 USB3.0/PCIe 数据采集扩展板。
- MIG 工程的 DDR3 数据率、AXI/Native 用户接口宽度和实测读写效率。
- 1080P 输出采用 30 Hz，还是采用更兼容的 60 Hz 并把每个算法帧重复显示两次。

在这四项没有确认前，不能在申请材料中写“已经具备 HDMI 实时输入输出”。可写成“完成 HDMI 输出，实时输入接口按板卡配件选择扩展”。

## 3. 一条视频通路到底包含什么

推荐把系统拆成以下模块：

```text
输入源
  │  视频像素 + 行/帧同步
  ▼
输入接收/解码 ──> RGB→YCbCr ──┬─> Y：超分模型 ───────────┐
                               └─> Cb/Cr：2×插值/延时对齐 ─┤
                                                           ▼
                                             YCbCr→RGB / 画面叠加
                                                           │
                                         帧缓存与跨时钟域（可选）
                                                           │
                                                           ▼
                                                 时序发生器 + HDMI TX
```

本模型只处理亮度 `Y`。若最终显示彩色视频，不能简单丢弃颜色：`Cb/Cr` 要用双线性或双三次方法放大，并经过匹配延迟后与模型输出 Y 合并。第一版也可以把 Y 同时接到 R、G、B，输出灰度画面，用于优先验证模型。

### 3.1 AXI4-Stream 视频接口建议

模块之间建议统一使用类似 AXI4-Stream Video 的握手语义：

| 信号 | 含义 |
|---|---|
| `tdata` | 当前一个或多个像素的数据 |
| `tvalid` | 上游声明当前数据有效 |
| `tready` | 下游声明可以接收；二者同时为 1 才真正传输 |
| `tuser[0]` | 一帧第一个有效像素，SOF |
| `tlast` | 一行最后一个有效像素，EOL |

AMD UG934 规定 AXI4-Stream Video 只传有效图像，消隐、音频和辅助包不随该像素流传输；因此 AXI 流的平均有效载荷不能和 HDMI 线上的像素时钟直接画等号。参见 [UG934 信号接口](https://docs.amd.com/r/en-US/ug934_axi_videoIP/AXI4-Stream-Signaling-Interface)。

## 4. 带宽怎么计算

### 4.1 三个基本公式

有效像素率：

```text
Pactive = Width × Height × FPS                    [pixel/s]
```

有效载荷带宽：

```text
Bactive = Pactive × BytesPerPixel                 [byte/s]
```

含消隐的峰值像素带宽：

```text
Fpixel = Htotal × Vtotal × FPS                    [Hz]
Bpeak  = Fpixel × BitsPerPixel                    [bit/s]
```

例如 RGB888 每像素有 R、G、B 三个 8-bit 分量，因此：

```text
8 bit + 8 bit + 8 bit = 24 bit = 3 byte/pixel
```

AMD 的视频系统指南也将平均带宽与含消隐峰值带宽分开计算，见 [UG934 视频带宽要求](https://docs.amd.com/r/en-US/ug934_axi_videoIP/Video-Subsystem-Bandwidth-Requirements)。

### 4.2 本项目有效载荷

| 数据格式 | 960×540@30 输入 | 1920×1080@30 输出 | 输入+输出 |
|---|---:|---:|---:|
| Y8，1 B/pixel | 15.552 MB/s | 62.208 MB/s | 77.760 MB/s |
| YCbCr 4:2:0 8-bit，1.5 B/pixel | 23.328 MB/s | 93.312 MB/s | 116.640 MB/s |
| YCbCr 4:2:2 8-bit，2 B/pixel | 31.104 MB/s | 124.416 MB/s | 155.520 MB/s |
| RGB888，3 B/pixel | 46.656 MB/s | 186.624 MB/s | 233.280 MB/s |

以输入 RGB888 为例：

```text
960 × 540 × 30 × 3 = 46,656,000 byte/s = 46.656 MB/s
```

这里使用十进制 `MB/s`；若操作系统按 `MiB/s` 显示，数值会略小，因为 `1 MiB = 1,048,576 byte`。

### 4.3 不同分辨率为何迅速变难

下表是 RGB888 的有效图像载荷，尚未包含 HDMI 消隐和协议开销：

| 模式 | 有效像素率 | RGB888 有效载荷 |
|---|---:|---:|
| 540P30 | 15.552 Mpixel/s | 46.656 MB/s |
| 1080P30 | 62.208 Mpixel/s | 186.624 MB/s |
| 1080P60 | 124.416 Mpixel/s | 373.248 MB/s |
| 4K30 | 248.832 Mpixel/s | 746.496 MB/s |
| 4K60 | 497.664 Mpixel/s | 1,492.992 MB/s |
| 8K30 | 995.328 Mpixel/s | 2,985.984 MB/s |
| 8K60 | 1,990.656 Mpixel/s | 5,971.968 MB/s |

从 1080P 到 4K，宽和高都变为 2 倍，所以像素数和同帧率计算量都是 4 倍；从 1080P 到 8K则是 16 倍。这就是 4K/8K 不能只看“K”字样、必须同时核算帧率和每像素位数的原因。

标准时序还包含消隐。例如 1080P60 的有效像素率为 124.42 MHz，但典型像素时钟为 148.50 MHz；720P60 的典型像素时钟为 74.25 MHz。参见 AMD [UG934 典型视频格式表](https://docs.amd.com/r/en-US/ug934_axi_videoIP/Typical-Video-Formats)。

## 5. DDR 带宽核算

### 5.1 理论带宽不是实测带宽

32-bit DDR3 的理论带宽为：

```text
BDDR,theory = TransferRate × 32 bit ÷ 8
```

| 配置示例 | 理论带宽 |
|---|---:|
| DDR3-800，32-bit | 3.200 GB/s |
| DDR3-1066，32-bit | 4.264 GB/s |
| DDR3-1600，32-bit | 6.400 GB/s |

这只是公式示例，不代表当前板卡已经按相应速率稳定运行。刷新、读写切换、行未命中、短突发、地址不连续和仲裁都会降低有效带宽。AMD 也明确指出 MIG 延迟与效率取决于访问模式，应该用目标访问行为进行仿真和板上测试，见 [UG586](https://docs.amd.com/r/en-US/ug586_7Series_MIS/DDR3-and-DDR2-SDRAM-Memory-Interface-Solution)。工程预算建议至少保留 30% 余量。

### 5.2 只存输入输出帧时

如果一帧要“写入 DDR 一次，再读出一次”，DDR 流量是有效视频载荷的 2 倍：

| 格式 | 输入帧写+读、输出帧写+读 |
|---|---:|
| Y8 | 155.520 MB/s |
| YCbCr 4:2:0 8-bit | 233.280 MB/s |
| YCbCr 4:2:2 8-bit | 311.040 MB/s |
| RGB888 | 466.560 MB/s |

双缓冲会使占用容量翻倍，却不会自动让稳定态带宽翻倍，因为同一时刻是写当前帧、读上一帧。额外带宽来自每个帧真正发生了几次读写，而不是“有几个缓冲区”。

若采用推荐的 `算法 30 FPS + HDMI 1080P60` 重复显示，输出帧每秒写 30 次、读 60 次，带宽要重新按真实读写次数计算。连同输入帧每秒写 30 次、读 30 次，Y8 总流量为：

```text
输入：960×540×1 B×(30 次写 + 30 次读)       = 31.104 MB/s
输出：1920×1080×1 B×(30 次写 + 60 次读)    = 186.624 MB/s
合计                                         = 217.728 MB/s
```

如果帧缓存保存 RGB888，同一策略约为 `653.184 MB/s`。这仍明显小于中间特征逐层落 DDR 的额外 `3.1104 GB/s`，但应加入 MIG 实测预算。

### 5.3 把中间特征写 DDR 时

本模型在 960×540 网格上的主要中间数据为：

| 中间结果 | 数据类型 | 每帧大小 |
|---|---|---:|
| Feature，16 通道 | INT16 | 16.5888 MB |
| Shrink，8 通道 | INT16 | 8.2944 MB |
| Mapping，8 通道 | INT16 | 8.2944 MB |
| Expand，16 通道 | INT16 | 16.5888 MB |
| 4 个子像素相位 | UINT8 | 2.0736 MB |
| 合计 |  | 51.8400 MB |

若每个结果写一次并读一次：

```text
51.84 MB/frame × 2 × 30 frame/s = 3.1104 GB/s
```

这还没计输入输出帧。该方案即使名义 DDR 峰值够，也会因多个读写端口、短突发和实时性压力变得危险。因此模型层之间必须流式连接，DDR 最多保存完整视频帧，不保存每层完整特征图。

## 6. 片上流式模型

### 6.1 行缓存而不是整帧缓存

卷积只需要当前像素附近的窗口。以宽度 960 为例，理论最低行缓存为：

| 层 | 最低行缓存 | 大小 |
|---|---|---:|
| Feature `5×5`，输入 Y8 | 4 行 × 960 × 1 B | 3,840 B |
| Mapping `3×3`，8ch INT16 | 2 行 × 960 × 8 × 2 B | 30,720 B |
| Subpixel `5×5`，16ch INT16 | 4 行 × 960 × 16 × 2 B | 122,880 B |
| 合计 |  | 157,440 B，约 153.75 KiB |

实际还要加边界填充、FIFO、存储体分割、并行读端口和跨时钟缓存，但数量级仍远小于把 51.84 MB 中间特征放入 DDR。

模型 INT8 权重约 2,832 byte；加上 INT32 偏置和 Q1.15 PReLU 等仍只有数 KB，适合全部常驻 BRAM/ROM。

### 6.2 算力与并行度

| 层 | MAC/帧 | 30 FPS 算力 | 占总计算量 |
|---|---:|---:|---:|
| Feature `5×5, 1→16` | 207.3600 M | 6.2208 GMAC/s | 14.12% |
| Shrink `1×1, 16→8` | 66.3552 M | 1.9907 GMAC/s | 4.52% |
| Mapping `3×3, 8→8` | 298.5984 M | 8.9580 GMAC/s | 20.34% |
| Expand `1×1, 8→16` | 66.3552 M | 1.9907 GMAC/s | 4.52% |
| Subpixel `5×5, 16→4` | 829.4400 M | 24.8832 GMAC/s | 56.50% |
| 合计 | 1,468.1088 M | 44.0433 GMAC/s | 100% |

每个 LR 像素需要恰好 `2,832 MAC`。如果每个 DSP 每周期完成 1 个 MAC，则不计任何损耗的最低并行 MAC 数为：

| 核心时钟 | 理想最低 MAC/周期 |
|---|---:|
| 100 MHz | 440.43 |
| 150 MHz | 293.62 |
| 180 MHz | 244.68 |
| 200 MHz | 220.22 |

这不是最终 DSP 数量承诺。不同位宽可以做 DSP 打包，累加树也会占 LUT/DSP；同一 DSP 是否能无空泡复用要由 RTL 结构、综合和时序决定。最值得优先并行化的是占 56.5% 计算量的 Subpixel Head。

### 6.3 PixelShuffle 的输出节拍

每输入 1 个 LR 像素，网络输出 4 个相位值，对应一个 `2×2` HR 像素块。于是：

```text
15.552 M LR pixel/s × 4 = 62.208 M HR pixel/s
```

可选结构：

- 网络并行产生 4 相位，通过 4-pixel-per-clock 宽总线输出。
- 先把 4 相位写入小 FIFO，再以更快输出时钟串行送出。
- 写入 DDR 帧缓存，再由固定 HDMI 像素时钟读出。

第一种延迟最低，第三种最容易解决 30 FPS 算法帧与 60 Hz 显示时序不一致的问题。

## 7. 推荐的两阶段通路

### 7.1 阶段 A：最小可交付闭环

```text
PC 生成 540P Y8 测试帧
        │ JTAG/UART/PCIe 初始化，或打包进 ROM
        ▼
DDR3/ROM 帧源 → 流式 INT8 超分核 → 1080P Y 帧缓存
                                      │
                            Y→RGB 灰度复制 + OSD
                                      │
                         1080P60 时序（每帧显示两次）
                                      ▼
                                  HDMI TX
```

验收重点：

- Golden 输入输出逐像素一致。
- 画面不撕裂、不滚屏，连续运行 30 分钟。
- 显示 `frame_counter`、核处理周期、FIFO 溢出/欠载标志。
- 拨码或按键切换 Bicubic/模型输出，便于现场对比。

这一路线不依赖尚未确认的 HDMI RX，最适合作为近期工程目标。

### 7.2 阶段 B：真实实时输入

| 输入方案 | 带宽是否够 | 难度 | 评价 |
|---|---|---:|---|
| 外接 HDMI RX 芯片/扩展板 | 取决于器件和引脚 | 高 | 演示最好，但需先确认硬件、电平、像素时钟和驱动 |
| 千兆以太网 UDP | 540P30 RGB888 约 373 Mb/s，理论可容纳 | 中高 | 需要 UDP 接收、丢包处理和帧缓冲；没有 ARM 辅助 |
| PCIe DMA | 远高于所需视频载荷 | 高 | 主机传输稳定，但 IP、驱动和 DMA 联调工作较重 |
| 摄像头并口/MIPI 转接 | 取决于模块 | 中高 | 可做实时采集，但分辨率和转接器必须匹配 |

由于 ACX750 没有 ARM/PS，不能写“Python 在板端配置 Overlay”。控制可选：拨码/按键、UART 寄存器、MicroBlaze 软核，或 PCIe/以太网主机控制。

## 8. 时钟域与帧率策略

建议至少分三个时钟域：

- `input_clk`：由输入接口或帧源决定。
- `core_clk`：卷积核高频时钟，目标先按 150–180 MHz 评估。
- `pixel_clk_out`：HDMI 输出时钟。1080P60 的典型像素时钟是 148.5 MHz，1080P30 通常为 74.25 MHz。

跨时钟域只能使用异步 FIFO、双口 RAM 或经过验证的 CDC 结构，不可直接跨域采样 `valid/data`。如果显示器对 1080P30 兼容性不好，推荐输出 1080P60：算法每秒生成 30 帧，帧缓存把每帧读取两次。这样算法吞吐要求不变，显示链路更通用。

`960×540` 不是常见消费级 HDMI 输入时序。即使以后增加 HDMI RX，普通电脑也未必会按该模式输出。实际输入可选择：

- 主机通过 PCIe/以太网直接发送 960×540 数据；
- 接收 1080P 后先做 2×降采样，作为演示输入；
- 接收标准 720P 后裁剪/缩放到 960×540，但会增加预处理模块。

## 9. 本次竞赛可以量化的指标

| 类别 | 必测指标 | 测法 |
|---|---|---|
| 通路 | 输入/输出分辨率、刷新率 | ILA 计数 SOF/EOL；显示器信息页 |
| 吞吐 | LR 帧率、HR 帧率、有效像素/秒 | 硬件帧计数器按 1 秒窗口统计 |
| 延迟 | 首个 LR 像素到首个 HR 像素的周期 | 两端打时间戳；区分核延迟和整帧缓存延迟 |
| DDR | 平均/峰值读写 MB/s | MIG/AXI 计数器，按读写字节数除以时间 |
| 稳定性 | 欠载、溢出、丢帧、同步丢失 | 粘滞错误寄存器 + ILA |
| 算力 | 实际 MAC/s、DSP 利用率 | 帧率 × 1.4681088 GMAC；综合报告 |
| 资源 | LUT、FF、BRAM、DSP | Vivado utilization report |
| 时序 | WNS、核心最高频率 | post-route timing report |
| 画质 | PSNR、SSIM、局部放大图 | 离线有真值数据集；直播画面不声称有 PSNR |
| 功耗 | 总功耗或动态功耗估计 | 板上测量优先，XPE/Vivado 估计需注明 |

答辩中最有说服力的对比不是只报“1080P”，而是同时展示：

```text
Bicubic / 模型模式在线切换
+ 同一画面局部细节
+ 30 FPS 实测计数
+ 端到端延迟
+ DDR 带宽下降（流式 vs 中间特征落 DDR 的估算或实验）
+ LUT/FF/BRAM/DSP 与功耗
```

| P1 | 当前模型只输出 Y | 第一版灰度；第二版补 Cb/Cr 插值和色彩转换 |
| P1 | 960×540 非常规 HDMI 输入 | 选择主机数据流，或增加标准时序预缩放 |
| P2 | 理论 133.2 GMAC/s 不能代表可实现性能 | 以 post-route Fmax、实测帧率和 DSP 利用率为准 |

推荐下一步顺序：

1. 用 Vivado 建立 `HDMI TX 彩条/灰度帧` 工程，确认 1080P60 输出。
2. 建立 MIG DDR3 带宽测试，分别测连续写、连续读、读写各半。
3. 只综合计算量最大的 `5×5, 16→4` Subpixel Head，得到真实 Fmax/DSP/BRAM。
4. 将已有全尺寸整数 Golden 作为 ROM/DDR 输入，对拍模型输出。
5. 完成阶段 A 后，再根据老师提供的硬件选择 HDMI RX、PCIe 或千兆网输入。
